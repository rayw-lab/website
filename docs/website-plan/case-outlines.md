# 个人网站旗舰案例大纲（第一版）

> 本文档定义个人网站「案例」板块第一版的三个旗舰案例大纲，以及后续扩展用的候选案例索引表。
> 每个案例按统一的 12 模块结构撰写，未确认的事实以【待填】占位，结构保持完整。

---

## 0. 撰写原则与案例卡片规范

### 0.1 撰写原则

调研结论：案例呈现的核心是 **「为什么这样判断」**，而非「项目成功」。读者（招聘方、合作方）真正想看的是判断依据、约束条件下的取舍过程，以及可迁移的方法论。

| 原则 | 说明 |
| --- | --- |
| 判断优先于结果 | 每个案例的重心放在「核心判断」「取舍」「失败复盘」三个模块，结果模块只陈述可验证的事实 |
| 目标值与实际值分离 | 所有量化表述必须标注是「目标值」还是「实际值」；未经验证的数据一律不写入「结果」模块 |
| 脱敏先行 | 每个案例必须有明确的信息边界声明；涉及具体厂商、平台参数、商务数据的内容按声明方式处理后才可公开 |
| 结构统一 | 三个案例均使用相同的 12 模块结构，便于横向比较与后续维护 |

### 0.2 案例卡片规范（列表页展示）

每个案例在网站列表页以卡片形式呈现，卡片包含以下五个字段：

| 字段 | 要求 | 示例形式 |
| --- | --- | --- |
| 一句话问题 | 以问题（而非成果）开头，点出案例要回答的核心疑问 | 「多语种座舱到底难在哪？」 |
| 角色 | 我在其中的实际职责，避免夸大 | 「产品规划负责人 / 方案主导者」 |
| 关键产物 | 1–2 个最有代表性的交付物名称 | 「多语种能力地图」「能力分层矩阵」 |
| 结果 | 一句可验证的事实陈述；无可验证结果时写推进状态 | 「方案被采纳并进入量产排期」 |
| 查看链接 | 指向案例详情页的路由 | `/cases/multilingual-cockpit` |

### 0.3 十二模块结构定义

| 序号 | 模块 | 回答的问题 |
| --- | --- | --- |
| 1 | 一句话摘要 | 这个案例在 30 字内讲清楚是什么 |
| 2 | 背景 | 问题发生在什么业务场景、什么时间点 |
| 3 | 约束 | 资源、时间、技术、组织上有哪些硬限制 |
| 4 | 我的角色 | 我具体负责什么、决策权边界在哪 |
| 5 | 核心判断 | 我做出了哪些关键判断、依据是什么 |
| 6 | 方案路径 | 从判断到落地走了哪几步 |
| 7 | 关键产物 | 产出了哪些可指认的交付物 |
| 8 | 结果 | 有哪些可验证的实际结果（不含目标值） |
| 9 | 取舍 | 放弃了什么、为什么放弃 |
| 10 | 失败复盘 | 哪些地方走错了、如果重来会怎么做 |
| 11 | 可复用方法 | 沉淀出哪些可迁移到其他场景的方法 |
| 12 | 信息边界/脱敏说明 | 哪些信息做了处理、以什么方式处理 |

## 案例A：海外多语种智能座舱——从语种清单到可量产能力地图

**卡片信息**

| 字段 | 内容 |
| --- | --- |
| 一句话问题 | 为什么多语种座舱不是「把界面翻译一遍」，而是一张能力地图？ |
| 角色 | 【待填：如 海外座舱产品规划负责人】 |
| 关键产物 | 多语种可量产能力地图、语种优先级决策框架 |
| 结果 | 【待填：一句可验证的事实，如「地图被纳入 XX 平台量产规划」】 |
| 查看链接 | `/cases/multilingual-cockpit`（占位，按最终路由调整） |

### A-1 一句话摘要

把「支持 N 种语言」的模糊需求，拆解为语言成熟度、芯片、生态、法规、成本、冻结节奏六个维度的可量产能力地图，让多语种座舱从翻译工程升级为产品规划问题。

### A-2 背景

- 业务场景：【待填：出海车型/区域市场背景，如进入欧洲、中东、东南亚等市场的座舱产品规划】
- 时间点与触发事件：【待填：如某车型立项、某区域法规节点】
- 起始状态：需求方以「语种清单」形式提出要求，默认多语种 = 界面与语音的翻译工作量问题
- 问题暴露：不同语种在语音识别/合成/大模型能力、内容生态、当地法规上的差距远超翻译范畴

### A-3 约束

| 约束类别 | 具体内容 |
| --- | --- |
| 技术 | 各语种的 ASR/TTS/NLU/大模型成熟度差异大；部分小语种无可用供应商方案【待填：具体语种】 |
| 芯片 | 不同区域车型搭载的座舱芯片平台算力不同，制约端侧语音与模型能力【待填：抽象化的平台档位】 |
| 生态 | 各区域内容与服务生态（导航、音乐、语音助手第三方服务）可用性不一 |
| 法规 | 数据出境、隐私合规、当地语言强制要求等区域法规【待填：涉及区域】 |
| 成本 | 每新增一个语种的授权、适配、测试、运营成本；预算上限【待填】 |
| 节奏 | 车型软件冻结节点倒排，语种能力必须匹配冻结节奏而非「越多越好」 |

### A-4 我的角色

- 职责范围：【待填：如 主导多语种座舱能力规划，输出语种优先级与量产方案】
- 决策权边界：【待填：哪些由我拍板、哪些需上升决策】
- 协作方：【待填：如 语音供应商、区域市场团队、法务合规、平台工程团队】

### A-5 核心判断

1. **多语种座舱不是翻译工程，而是六维能力问题**：语言成熟度 × 芯片平台 × 内容生态 × 区域法规 × 单语种成本 × 冻结节奏，任何一维不达标都会导致该语种不可量产。
2. **语种清单必须转化为能力地图**：以「语种 × 能力维度」矩阵替代扁平清单，每个格子标注成熟度等级与阻塞项，使「支持某语种」成为可验证的工程承诺而非口头承诺。
3. **优先级由可量产性决定，而非市场声量**：【待填：具体判断依据，如某高声量语种因法规/生态缺口被降级的判断过程】
4. **冻结节奏是第一约束**：能力地图必须与车型软件冻结节点对齐，宁可减语种保节点，不为凑语种拖节奏。

### A-6 方案路径

1. 收集需求方语种清单，逐语种盘点六个维度的现状（供应商能力、平台适配、生态、法规、成本、时间）
2. 定义各维度的成熟度分级标准【待填：分级定义】
3. 构建「语种 × 维度」能力地图，标注每格的等级、阻塞项与解锁条件
4. 基于地图输出语种分批策略：首发批 / 后续 OTA 批 / 暂不承诺批【待填：具体分批】
5. 与冻结节点对齐，形成可量产的多语种路线图并推动各方对齐【待填：对齐过程关键节点】

### A-7 关键产物

| 产物 | 形态 | 网站呈现方式 |
| --- | --- | --- |
| 多语种可量产能力地图 | 语种 × 六维度矩阵 | 脱敏后的示意版矩阵图【待填：重绘】 |
| 语种优先级决策框架 | 决策树 / 打分规则 | 方法论图示 |
| 分批量产路线图 | 时间轴 | 抽象时间轴（隐去具体日期与车型） |
| 【待填：其他产物】 | 【待填】 | 【待填】 |

### A-8 结果

> 只写经过验证的实际值；目标值写入 A-6 方案路径或删除。

- 【待填：实际值1，如「首发批 X 个语种按冻结节点交付」】
- 【待填：实际值2，如「能力地图被后续车型规划复用」】
- 尚无法验证的部分如实标注推进状态：【待填】

### A-9 取舍

| 放弃项 | 原因 | 代价 |
| --- | --- | --- |
| 【待填：如 某市场声量高但生态缺失的语种】 | 【待填：六维中的具体短板】 | 【待填：如 区域团队的阻力、市场宣传口径调整】 |
| 【待填：如 全语种统一体验目标】 | 分档体验换取节点达成 | 【待填】 |

### A-10 失败复盘

- 【待填：判断失误1，如 初期低估某语种法规审批周期，导致排期返工】
- 【待填：判断失误2，如 对某供应商能力评估依赖演示而非实测】
- 如果重来：【待填：改进做法】

### A-11 可复用方法

1. **「清单 → 地图」转化法**：任何以清单形式提出的多目标需求，先升维成「目标 × 约束维度」矩阵再谈优先级。
2. **可量产性优先级模型**：优先级 = f(能力成熟度, 阻塞项解锁成本, 节点匹配度)，而非市场声量单变量。
3. **冻结节奏对齐法**：以软件冻结节点为硬约束倒排能力承诺，把「做不做」的争论转化为「哪一批做」的排期问题。

### A-12 信息边界/脱敏说明

- **公开方式：匿名化。** 不出现公司名、车型名、供应商名、具体区域组合。
- 语种以「高资源语种/中资源语种/低资源语种」或字母代号表述，不给出可反推市场策略的完整语种组合。
- 所有矩阵、路线图为脱敏重绘的示意版，日期用相对时间（T0/T0+n）表述。
- 成本与商务数据不出现具体数字，仅描述数量级关系或省略。
- 【待填：需额外确认的敏感项清单】

## 案例B：不同芯片平台下，汽车大模型能力应该如何分层

**卡片信息**

| 字段 | 内容 |
| --- | --- |
| 一句话问题 | 当芯片平台参差不齐时，大模型能力怎么分层才不至于「高配演示、低配翻车」？ |
| 角色 | 【待填：如 座舱 AI 能力架构方案主导者】 |
| 关键产物 | 大模型能力分层矩阵、端云分工与降级策略 |
| 结果 | 【待填：一句可验证的事实】 |
| 查看链接 | `/cases/llm-capability-layering`（占位，按最终路由调整） |

### B-1 一句话摘要

面对算力差异巨大的多个座舱芯片平台，把大模型能力拆解为端侧/云端/降级三条路径与语音车控的明确分工，形成「平台不可复制」前提下的能力分层架构。

### B-2 背景

- 业务场景：【待填：如 多平台并存的车型矩阵引入大模型能力】
- 起始状态：大模型能力规划以「旗舰平台」为基准，低算力平台的可行性与体验未被认真定义
- 问题暴露：高配平台上的演示效果无法在低配平台复现；端云边界、断网降级、语音车控与大模型的关系均无明确定义
- 时间点：【待填】

### B-3 约束

| 约束类别 | 具体内容 |
| --- | --- |
| 芯片算力 | 多档平台并存，端侧可运行的模型规模差异大【待填：抽象档位划分，如 高/中/低算力档】 |
| 内存与带宽 | 端侧模型常驻内存与其他座舱应用争抢资源【待填：抽象量级】 |
| 网络 | 车载网络不稳定，云端能力必须有断网与弱网预案 |
| 时延 | 车控类指令有硬性响应时延要求，不能容忍云端往返抖动【待填:目标时延为设计目标值】 |
| 成本 | 云端推理成本随车队规模线性增长；单车云端预算【待填】 |
| 平台不可复制 | 各平台工具链、算子支持、供应商 SDK 互不兼容，旗舰方案无法直接移植 |

### B-4 我的角色

- 职责范围：【待填：如 主导能力分层架构定义，输出端云分工与降级策略】
- 决策权边界：【待填】
- 协作方：【待填：如 芯片供应商、语音团队、云平台团队、车控域团队】

### B-5 核心判断

1. **能力分层的基准应是「最低可交付平台」而非旗舰平台**：先定义低算力平台上必须成立的底线体验，再向上叠加，避免「高配演示、低配翻车」。
2. **端侧与云端按「确定性要求」分工，而非按「能力大小」分工**：安全相关与强时延约束的语音车控走端侧确定性链路；开放对话、内容生成类能力走云端；两者之间以明确的意图路由边界隔离。
3. **降级是一等公民**：断网/弱网/云端故障下的降级体验必须在架构层显式设计，而非事后补丁；每层能力都要定义其降级目标形态。
4. **平台不可复制，但分层框架可复制**：接受各平台实现不可移植的现实，把可复用性放在「分层框架 + 能力定义 + 验收标准」这一层，而非代码层。
5. 【待填：其他关键判断】

### B-6 方案路径

1. 盘点各芯片平台的算力、内存、工具链现状，抽象为若干能力档位【待填：档位定义】
2. 把大模型相关能力拆解为原子能力项（语音车控、闲聊问答、内容生成、多轮任务等）【待填：完整能力清单】
3. 为每个能力项定义端侧/云端/端云协同的归属规则与意图路由边界
4. 逐档位构建「平台档位 × 能力项」分层矩阵，标注每格的实现路径与降级形态
5. 定义降级策略：触发条件、降级后体验、恢复机制【待填：具体策略】
6. 输出各平台的能力承诺清单与验收标准，推动各域对齐【待填：对齐过程】

| 产物 | 形态 | 网站呈现方式 |
| --- | --- | --- |

| 端云分工与意图路由边界定义 | 架构图 + 规则文档 | 脱敏架构示意图 |
| 降级策略设计 | 状态机 / 策略表 | 简化状态图 |

- 【待填:实际值1，如「分层矩阵被 X 个平台的量产方案采用」】
- 【待填：实际值2，如 低算力平台底线体验通过验收的事实】
- 尚在推进的部分如实标注状态：【待填】

### B-9 取舍

| 放弃项 | 原因 | 代价 |
| --- | --- | --- |
| 【待填：如 低算力平台的某类端侧生成能力】 | 内存/时延无法达标，降级到云端或砍掉 | 【待填：体验差异带来的产品口径压力】 |
| 【待填：如 跨平台统一实现的诉求】 | 平台不可复制，统一实现成本远超收益 | 各平台需独立维护，人力分散 |
| 【待填】 | 【待填】 | 【待填】 |

### B-10 失败复盘

- 【待填：如 初期按旗舰平台定义体验，向下适配时大量返工的过程】
- 【待填：如 对某平台工具链成熟度过于乐观】
- 如果重来：【待填：如 一开始就从最低档平台立底线】

### B-11 可复用方法

1. **底线优先分层法**：多档硬件并存时，从最低可交付档定义底线体验，向上做增量，而不是从旗舰向下做减法。
2. **按确定性分工的端云边界**：以「确定性/时延/安全要求」而非「模型能力大小」划分端云职责。
3. **降级即设计**：把降级形态写进每个能力项的定义与验收标准，使其可测试、可承诺。
4. **框架层复用策略**：在不可复制的平台差异之上，抽取可复用的分层框架与验收标准层。

### B-12 信息边界/脱敏说明

- **公开方式：抽象平台参数。** 不出现芯片厂商名与具体型号，以「高/中/低算力档」或代号表述。
- 算力、内存、时延等参数只给数量级或相对关系，不给可反推具体平台的精确数值。
- 架构图重绘为通用示意，隐去供应商 SDK 与内部系统名称。
- 能力清单做泛化处理，不暴露未发布功能的具体规划。
- 【待填：需额外确认的敏感项清单】

### C-1 一句话摘要

把零散的「个人用 AI 工具」升级为端到端的 AI 原生工作流：识别真实瓶颈、定义自动化节点与输入输出契约、设置人工审核与防幻觉机制，并用效率/质量/返工三维指标评估——包括如实记录失败的实验。

### C-5 核心判断

1. **瓶颈不在「生成」而在【待填：实际瓶颈，如 信息收集/校对/格式对齐】**：先测量流程各环节耗时与返工来源，再决定 AI 介入点；「哪里能用 AI」不等于「哪里值得用 AI」。
2. **自动化节点必须有明确的输入输出契约**：每个 AI 节点定义输入格式、输出格式、质量标准与失败行为，否则节点之间无法串联，只能退回「人肉粘合」。
3. **人工审核点按风险分级设置**：高风险（事实性、对外承诺）环节强制人审，低风险环节抽检；审核点是工作流的一部分而非外挂。
4. **防幻觉靠机制不靠提示词**：【待填：具体机制，如 引用溯源、白名单数据源、结构化校验、双模型交叉核对等实际采用项】
5. **评估必须三维且区分目标/实际**：效率（耗时）、质量（错误率/合格率）、返工（返工率/返工耗时）三维同测；目标值用于立项，实际值用于结论，二者严禁混写。

### C-11 可复用方法

1. **瓶颈先于工具**：先测量流程、定位瓶颈，再选 AI 介入点；拒绝「拿着工具找钉子」。
2. **节点契约化**：每个自动化节点定义输入/输出/质量标准/失败行为四要素，使工作流可串联、可替换、可评估。
3. **风险分级审核**：按产出风险等级设置强制人审/抽检，把「人在环上」变成显式设计。
4. **三维评估 + 目标/实际分离**：效率、质量、返工同测；未验证数据不进结论。
5. **失败实验留档**：负收益实验与成功经验同等记录，是方法可信度的一部分。
